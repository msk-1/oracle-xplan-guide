実行計画は Id の順に実行されるわけではない。インデントから親子関係を読み取り、「親は子を上から順に呼ぶ」という規則で処理をたどる。

題材の SQL

顧客 42 の受注について、明細と商品名を出す。スクリプトは sql/ch02_reading_order.sql にある。

SELECT /*+ GATHER_PLAN_STATISTICS */
       o.order_id, o.order_date, p.name AS product, i.quantity
FROM   customers c
JOIN   orders o       ON o.customer_id = c.customer_id
JOIN   order_items i  ON i.order_id    = o.order_id
JOIN   products p     ON p.product_id  = i.product_id
WHERE  c.customer_id = 42
ORDER  BY o.order_id, i.line_no;

読む順番の規則

  1. インデントで親子を決める。 ある行の親は、それより上にあって、インデントが 1 段浅い最も近い行である
  2. 親は子を上から順に呼ぶ。 子が 2 つある結合では、上の子（第 1 子）を先に、下の子（第 2 子）を後に使う
  3. 行を最初に生み出すのは、第 1 子をたどり続けた先の葉である。葉とは、子を持たない行を指す

Id は上から振られた単なる番号である。実行の順番は表していない。

ツリーで描く

インデントを線に置き換えると、親子関係が見える。

0 SELECT STATEMENT
└─ 1 SORT ORDER BY

      │  ├─ 4 NESTED LOOPS                      ← 第 1 子（外側）
      │  │  ├─ 5 TABLE ACCESS BY INDEX ROWID BATCHED  ORDERS   ← 第 1 子（外側）
      │  │  │  └─ 6 INDEX RANGE SCAN  ORDERS_CUSTOMER_IX
      │  │  └─ 7 INDEX RANGE SCAN  ORDER_ITEMS_PK             ← 第 2 子（内側）
      │  └─ 8 TABLE ACCESS BY INDEX ROWID  ORDER_ITEMS        ← 第 2 子（内側）
      └─ 9 TABLE ACCESS FULL  PRODUCTS          ← 第 2 子（突き合わせる側）

実行の流れ

Id 0 から第 1 子をたどると、最初に行を生み出すのは Id 6 である。そこから親へ戻りながら処理が進む。

順 Id 処理
1 6 索引 ORDERS_CUSTOMER_IX で customer_id = 42 の ROWID を探す
2 5 その ROWID で ORDERS の行を読む（20 行）
3 7 受注 1 行ごとに、主キー索引で明細の ROWID を探す
4 4 受注と明細の ROWID を組み合わせる
5 8 明細の ROWID で ORDER_ITEMS の行を読む（39 行）
6 3 受注と明細の結合結果を返す
7 9 PRODUCTS を全件読む（1000 行）
8 2 明細の product_id で商品を突き合わせる
9 1 order_id, line_no で並べ替える
10 0 結果 39 行を返す

実行順は 6 → 5 → 7 → 4 → 8 → 3 → 9 → 2 → 1 → 0 となり、Id の順とは一致しない。

「いちばん深い行から読む」は正確ではない

よく「インデントが一番深い行から読む」と説明される。この計画ではたまたま当てはまるが、規則としては「第 1 子をたどった先の葉から」が正しい。 たとえば Id 9 は浅い位置にあるが、Id 3 の処理がすべて終わるまで動かない。

NESTED LOOPS — 外側の 1 行ごとに内側を実行する

NESTED LOOPS は、第 1 子（外側）が返す 1 行ごとに、第 2 子（内側）を 1 回実行する。Starts 列で確かめられる。

Id 操作 Starts E-Rows A-Rows
5 ORDERS（外側） 1 20 20
7 ORDER_ITEMS_PK（内側） 20 2 39
8 ORDER_ITEMS（内側） 39 2 39
  • Id 7 は、外側の受注 20 行に対して 20 回実行された
  • E-Rows は 1 回あたり の見積りである（受注 1 件につき明細 2 行）
  • A-Rows は 全実行の合計 である（20 回で 39 行）

見積りと実績を比べるときは、E-Rows × Starts と A-Rows を比べる。ここでは 2 × 20 = 40 に対し 39 で、見積りはほぼ正しい。

2 段の NESTED LOOPS

Id 3 と Id 4 は、どちらも ORDERS と ORDER_ITEMS の結合である。索引を引く段（Id 4）と表を読む段（Id 3）に分かれている。

  • Id 4: 受注 1 行ごとに、明細のROWID だけを索引から集める
  • Id 3: 集めた ROWID 1 つごとに、ORDER_ITEMS の行を読む（Id 8 の Starts = 39）

この形を NLJ batching という。表へのアクセスをまとめて行い、I/O を減らすための形である。読み方は通常の NESTED LOOPS と同じでよい。

HASH JOIN — 第 1 子でハッシュ表を作る

HASH JOIN（Id 2）は子を 2 つ持ち、それぞれ 1 回ずつ実行する。

  1. 第 1 子（Id 3） の結果 39 行を読み、結合キー product_id でメモリ上にハッシュ表を作る。この側を build 入力と呼ぶ
  2. 第 2 子（Id 9） の PRODUCTS 1000 行を 1 行ずつ読み、ハッシュ表を引いて一致する行を返す。この側を probe 入力と呼ぶ

ハッシュ表を作り終えるまで、HASH JOIN は 1 行も返さない。オプティマイザは通常、小さい方を第 1 子に置く。Used-Mem の 724K は、ハッシュ表に使ったメモリ量である。

Predicate Information — access と filter

Id に * が付いた行には条件があり、その中身が Predicate Information に表示される。

種類 意味 例
access 読む範囲を絞る条件。索引を引く、ハッシュ表を引くなどに使う 6 - access("O"."CUSTOMER_ID"=42)
filter 読んだ行を捨てるかどうかの条件。読む量は減らない 1 章の 4 - filter("O"."STATUS"='PENDING')

Id 6 は access なので、索引の customer_id = 42 の部分だけを読んでいる。Buffers が 2 と小さいのはそのためである。

1 章の Id 4 は filter である。ORDERS を全件読み、PENDING 以外の行を捨てていた。filter の行で A-Rows が少なく Buffers が多い場合は、無駄に読んで捨てていることを意味する。

CUSTOMERS が計画にない — 結合除去

SQL では CUSTOMERS を結合しているのに、計画に CUSTOMERS がない。これは結合除去（join elimination）による。オプティマイザは次の 3 点から、CUSTOMERS を結合しても結果が変わらないと判断した。

  • orders.customer_id は NOT NULL である
  • orders.customer_id は CUSTOMERS への外部キーなので、対応する顧客が必ず 1 行だけある
  • CUSTOMERS の列を SELECT していない

条件 c.customer_id = 42 は、結合条件を通して o.customer_id = 42 に置き換えられている（Id 6 の access）。

Note — adaptive plan

this is an adaptive plan は、実行時に結合方式を切り替えられる計画であることを示す。オプティマイザは NESTED LOOPS と HASH JOIN の両方を用意しておき、実際に流れた行数を見て、どちらを使うかを決める。表示されているのは、実際に使われた方式である。詳しくは 5 章で扱う。

まとめ

  • 実行計画は Id の順に動くわけではない。インデントで親子を決め、親は子を上から順に呼ぶ
  • 最初に動くのは、第 1 子をたどった先の葉である
  • NESTED LOOPS の内側は外側の行数だけ実行される。Starts を見て、E-Rows × Starts と A-Rows を比べる
  • HASH JOIN は第 1 子でハッシュ表を作り、第 2 子で突き合わせる
  • access は読む範囲を絞る条件、filter は読んだ後に捨てる条件である
  • SQL に書いた表が計画にないときは、結合除去を疑う
