アクセスパスとは、表から行を取り出す方法のことである。実行計画では、子を持たない行（葉）に現れる。結合や集計の行は、葉から受け取った行を加工しているだけである。行を実際に読んでいるのは葉なので、Buffers の大半も葉で発生する。

前提

ブロック・ROWID・索引の構造（B-tree）・複合索引は 4-1. 索引のしくみ で説明している。このページはそれを読んだ前提で進める。

INDEX UNIQUE SCAN — 主キーで 1 行を引く

SELECT order_date, amount FROM orders WHERE order_id = 12345;

-----------------------------------------------------------------------------------------
| Id  | Operation                   | Name        | Starts | E-Rows | A-Rows | Buffers |
-----------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT            |             |      1 |        |      1 |       3 |
|   1 |  TABLE ACCESS BY INDEX ROWID| ORDERS      |      1 |      1 |      1 |       3 |
|*  2 |   INDEX UNIQUE SCAN         | SYS_C008729 |      1 |      1 |      1 |       2 |
-----------------------------------------------------------------------------------------

   2 - access("ORDER_ID"=12345)
  • 主キーや一意索引に、等価条件（=）で 1 行だけを引くときに選ばれる
  • 索引を根から葉までたどって 2 ブロック、ROWID で表を 1 ブロック読み、合計 3 ブロックで済む
  • SYS_C で始まる名前は、主キー制約を作ったときにシステムが自動で付けた索引の名前である

TABLE ACCESS BY INDEX ROWID は、索引から得た ROWID（行の住所）を使って、表の行を直接読む操作である。

INDEX RANGE SCAN — 範囲や重複のある値を引く

SELECT COUNT(amount) FROM orders WHERE order_date = DATE '2024-03-01';

--------------------------------------------------------------------------------
| Id  | Operation         | Name           | Starts | E-Rows | A-Rows | Buffers |
--------------------------------------------------------------------------------
|   0 | SELECT STATEMENT  |                |      1 |        |      1 |       3 |
|   1 |  SORT AGGREGATE   |                |      1 |      1 |      1 |       3 |
|*  2 |   INDEX RANGE SCAN| ORDERS_DATE_IX |      1 |    200 |    200 |       3 |
--------------------------------------------------------------------------------

   2 - access("ORDER_DATE"=TO_DATE(' 2024-03-01 00:00:00', 'syyyy-mm-dd hh24:mi:ss'))
  • 一意でない索引に等価条件を指定したとき、または BETWEEN や > のような範囲条件を指定したときに選ばれる
  • 索引の葉を、条件に合う範囲だけ横にたどる

この計画には TABLE ACCESS がない。amount 列は NOT NULL なので、COUNT(amount) は行数を数えるのと同じ意味になる。行数は索引だけで数えられるため、表を読まずに答えが出ている。SQL が必要とする列がすべて索引にあれば、表を読まずに済む。

表も読む場合

amount の合計を求めると、値を取りに表を読む必要が生じる。

SELECT SUM(amount) FROM orders WHERE order_date = DATE '2024-03-01';

---------------------------------------------------------------------------------------------------

---------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT                     |                |      1 |        |      1 |     203 |
|   1 |  SORT AGGREGATE                      |                |      1 |      1 |      1 |     203 |
|   2 |   TABLE ACCESS BY INDEX ROWID BATCHED| ORDERS         |      1 |    200 |    200 |     203 |

ORDERS_DATE_IX は 3 段の木なので、索引はルート・ブランチ・葉の 3 ブロックで済んでいる。200 件分の項目が 1 枚の葉に収まったからである。ところが表は 200 ブロック（203 − 3）を読んでいる。

同じ日付の行はどこにあるか

2024-03-01 の行が入っているブロックを調べる。

SELECT order_id, DBMS_ROWID.ROWID_BLOCK_NUMBER(rowid) AS block_no
FROM   orders
WHERE  order_date = DATE '2024-03-01'
ORDER  BY order_id
FETCH  FIRST 5 ROWS ONLY;

SELECT COUNT(DISTINCT DBMS_ROWID.ROWID_BLOCK_NUMBER(rowid)) AS blocks, COUNT(*) AS cnt
FROM   orders
WHERE  order_date = DATE '2024-03-01';

  ORDER_ID   BLOCK_NO
---------- ----------
       425        140
      1425        155
      2425        152
      3425        170
      4425        178

    BLOCKS        CNT
---------- ----------
       200        200

200 件が 200 個の別々のブロックに入っている。

  • 日付は DATE '2023-01-01' + MOD(受注番号, 1000) で作ったので、同じ日付は受注番号 1000 番おきに現れる
  • 受注は番号順に 1 ブロック約 200 行ずつ入っているので、1000 番離れた行は必ず別のブロックにある
手順 読んだブロック
索引で 200 件の ROWID を調べる 3
ROWID ごとに表のブロックを読む（1 件 = 1 ブロック） 200
合計 203

200 件が 1 ブロックにまとまっていれば、3 + 1 = 4 ブロックで済んだ。同じ件数でも、行の置かれ方で約 50 倍の差がつく。

ブロック番号が 140 → 155 → 152 と単調に増えないのは、Oracle が表の領域をある程度まとまった単位で確保して割り当てるためである。

この「索引の順にたどると、1 行ごとに別のブロックへ移る」状態は、後述の CLUSTERING_FACTOR では ORDERS_DATE_IX の値 200,000（行数と同じ）として現れる。

同じ 200 件でも、受注番号 12345〜12544 を取ると結果が変わる。

FROM   orders

表は 5 − 3 = 2 ブロックしか読んでいない。

違いを生むのは値が連続しているかどうかではなく、INSERT した順番である。表のブロックには、行が INSERT した順に、空きのある場所から入る。

INSERT 順 →
受注番号:  …  424    425    426  …  1424   1425   1426  …  2425 …
日付:      …  2/29   3/1    3/2  …  2/29   3/1    3/2   …  3/1  …
                     ↑                     ↑                ↑
                 3/1 は 1000 件に 1 回しか INSERT されない

ブロック A: 受注 401〜600   → 日付はすべて違う 200 日分（3/1 は 425 の 1 件だけ）
ブロック B: 受注 601〜800   → 3/1 は 0 件
  …
ブロック F: 受注 1401〜1600 → 3/1 は 1425 の 1 件だけ

ブロックの区切りは説明用である。1 ブロックには連続して INSERT された約 200 件が入るので、次のようになる。

  • 受注番号は INSERT の順番と同じ順に増えるので、連続する番号は同じブロックにまとまる
  • 日付は 1 件ごとに次の日へ進んで循環するので、1 ブロックの 200 件はすべて違う日付になる。同じ日付の行は 200 個のブロックに散らばる

これが CLUSTERING_FACTOR の差として現れる。主キー索引は 960（表のブロック数 1000 とほぼ同じ）、ORDERS_DATE_IX は 200,000（行数と同じ）である。

まとまるかどうかは INSERT の順番で決まる

INSERT の順番と値の順番が一致する列（連番の ID、登録日時など）では、行がまとまる。 一致しない列では、連続する値でも行が散らばる。同じ値が続けて INSERT されれば 1 か所に集まり、間をあけて INSERT されれば散らばる。

散らばった行を索引で取る損益分岐点

行が散らばっていても、取る件数が少なければ索引のほうが得である。日付の範囲を広げながら、索引と FULL の Buffers を比べる。スクリプトは sql/ch04_breakeven.sql にある。

SELECT /*+ GATHER_PLAN_STATISTICS INDEX(orders orders_date_ix) */ SUM(amount)   -- 索引を強制
FROM   orders
WHERE  order_date BETWEEN DATE '2024-03-01' AND DATE '2024-03-01' + 日数 - 1;
-- 同じ SQL を FULL(orders) ヒント版と、ヒントなし版でも実行する
日数 件数 索引の Buffers FULL の Buffers オプティマイザが選んだ方式
1 200 203 1004 索引
3 600 605 1004 FULL
5 1,000 1006 1004 FULL
10 2,000 2008 1004 FULL
30 6,000 6019 1004 FULL

1 日分の条件は BETWEEN 同じ日 AND 同じ日 なので、オプティマイザが等価条件（=）に書き換えている。

読み取れることは次のとおり。

  • 索引の Buffers は件数にほぼ比例する。 行が 1 件ずつ別のブロックにあるので、1 件ごとに 1 ブロック読む
  • FULL の Buffers は件数によらず一定（1004）である。 何件取っても表を一度全部読むだけである
  • 30 日分では、索引は表全体の約 6 倍を読む。 同じブロックを何度も読み直しているためである。表は 1000 ブロックしかないのに、6000 件分のブロックを 1 件ずつ取りに行っている

3 日分で、Buffers の少ない索引ではなく FULL が選ばれた理由

3 日分では、索引は 605、FULL は 1004 で、Buffers だけを見れば索引のほうが少ない。それでもオプティマイザは FULL を選んだ。

理由は、1 回の読み込みで読めるブロック数が違うことにある。

方式 読み込み方
索引から表を読む ROWID ごとに 1 ブロックずつ読む（シングルブロック読み込み）
TABLE ACCESS FULL 隣り合う複数のブロックを 1 回でまとめて読む（マルチブロック読み込み）

Buffers は、どちらの読み方でも 1 ブロックを 1 と数える。一方、オプティマイザの Cost（3 章）は、まとめて読めるぶん FULL を安く見積もる。そのため、Buffers では索引が少なくても、Cost では FULL が小さくなることがある。

Buffers は「読んだブロックの量」の比較には便利だが、読み方の違いは表さない。境目に近いケースでは、Buffers の差がそのまま実行時間の差になるとは限らない。

RANGE SCAN が有効かを判断する

判断の方法は 2 つある。実行した計画で確かめる方法と、実行前に見積もる方法である。

方法 1: 実行した計画で確かめる

ALLSTATS LAST で計画を取り、次の 3 点を見る。

① 表アクセスの Buffers を、表全体のブロック数と比べる

TABLE ACCESS BY INDEX ROWID の自分の Buffers（自分の値 − 索引の値）が、表のブロック数（USER_TABLES.BLOCKS）に近い、または超えているなら、索引の効果はない。前の節の 30 日分（6019 ブロック、表は 1000 ブロック）がこれにあたる。

② 索引で見つけた行が、表で捨てられていないかを見る

索引の A-Rows と、その親の TABLE ACCESS BY INDEX ROWID の A-Rows を比べる。親の行に filter が付いていて、A-Rows が大きく減っている場合、索引で見つけた行の大半を、表を読んでから捨てている。

SELECT /*+ GATHER_PLAN_STATISTICS INDEX(orders orders_date_ix) */ SUM(amount) FROM orders
WHERE order_date BETWEEN DATE '2024-03-01' AND DATE '2024-03-02' AND amount > 49000;

この場合は、条件の列をすべて含む複合索引（例: (order_date, amount)）を作れば、索引の中で 16 行まで絞り込める。そうすれば、表を読むのは 16 行分で済む。複合索引の作り方と列の順番は、この章では扱わない。

③ FULL ヒントの計画と比べる

迷ったら、FULL(表名) ヒントを付けた計画も取り、Buffers と A-Time を並べて比べる。前の節の表は、この方法で作った。

方法 2: 実行前に見積もる

表を読むブロック数は、CLUSTERING_FACTOR からおおよそ見積もれる。

表を読むブロック数 ≒ CLUSTERING_FACTOR × (取り出す行数 ÷ 表の行数)

これを表のブロック数（ここでは 1000）と比べる。オプティマイザも、ほぼ同じ考え方で索引の Cost を計算している。

例 CLUSTERING_FACTOR 取り出す行数 見積り 実測（表の分）
日付 1 日 200,000 200 200,000 × 200 / 200,000 = 200 200（203 − 3）
日付 3 日 200,000 600 200,000 × 600 / 200,000 = 600 600（605 − 5）
受注番号 12345〜12544 960 200 960 × 200 / 200,000 ≒ 1 2（5 − 3）

見積りが表のブロック数よりずっと小さければ、RANGE SCAN は有効である。表のブロック数に近づくなら、FULL を検討する。

TABLE ACCESS FULL — 表を全部読む

SELECT COUNT(*) FROM orders WHERE amount > 49000;

----------------------------------------------------------------------------
| Id  | Operation          | Name   | Starts | E-Rows | A-Rows | Buffers |
----------------------------------------------------------------------------
|   0 | SELECT STATEMENT   |        |      1 |        |      1 |    1004 |
|   1 |  SORT AGGREGATE    |        |      1 |      1 |      1 |    1004 |
|*  2 |   TABLE ACCESS FULL| ORDERS |      1 |   5996 |   5996 |    1004 |
----------------------------------------------------------------------------

   2 - filter("AMOUNT">49000)
  • 使える索引がないとき、または表の大部分を読むときに選ばれる
  • 表の全ブロック（約 1000）を読む。複数のブロックをまとめて読むので、1 ブロックあたりの負担は索引より軽い
  • 条件は filter になる。すべての行を読んだあとで、条件に合わない行を捨てるという意味である。access のように、読む範囲を絞る条件ではない

TABLE ACCESS BY INDEX ROWID BATCHED

次の節の計画に出てくる。索引から得た ROWID を 1 件ずつ使うのではなく、いくつかまとめて、ブロックの順に並べ替えてから表を読む最適化である。同じブロックを何度も読み直さずに済む。読み方は TABLE ACCESS BY INDEX ROWID と同じでよい。

「索引のほうが速い」とは限らない

status 列の索引を使った場合と使わなかった場合を比べる。

SELECT SUM(amount) FROM orders WHERE status = 'SHIPPED';                                      -- F1
SELECT /*+ INDEX(orders orders_status_ix) */ SUM(amount) FROM orders WHERE status = 'SHIPPED'; -- F2
SELECT SUM(amount) FROM orders WHERE status = 'PENDING';                                      -- G1
SELECT /*+ INDEX(orders orders_status_ix) */ SUM(amount) FROM orders WHERE status = 'PENDING'; -- G2

条件 取り出す行 FULL の Buffers 索引の Buffers
SHIPPED 196,000（98%） 1004 1483
PENDING 3,000（1.5%） 1004 970

SHIPPED: ほとんどの行を取るなら索引は損

98% の行を取るなら、どのみち表のほぼ全ブロックを読むことになる。索引を使うと、その上に索引の 523 ブロックを読む分だけ損をする。

PENDING: 1.5% しか取らないのに、ほとんど得をしない

取り出すのは 3000 行だけなのに、索引経由でも表を 959 ブロック（970 − 11）読んでいる。表全体（約 1000 ブロック）とほぼ同じである。

原因は、PENDING の行が表全体に散らばっていることである。データを作るとき、200 行ごとに 3 行を PENDING にした（sql/01_schema.sql）。1 ブロックにはおよそ 200 行入るので、ほぼすべてのブロックに PENDING の行が含まれる。3000 行を拾い集めるには、結局ほぼ全ブロックを読む必要がある。

索引が効くかどうかは、読む行数だけでは決まらない。その行がどれだけ少ないブロックにまとまっているかも効く。

CLUSTERING_FACTOR — 行のまとまり具合の指標

USER_INDEXES.CLUSTERING_FACTOR は、索引をキーの順にたどったとき、表のブロックが切り替わった回数である。

SELECT index_name, clustering_factor, num_rows, leaf_blocks
FROM   user_indexes WHERE table_name = 'ORDERS' ORDER BY clustering_factor;

INDEX_NAME           CLUSTERING_FACTOR   NUM_ROWS LEAF_BLOCKS
-------------------- ----------------- ---------- -----------
SYS_C008729                        960     200000         374
ORDERS_STATUS_IX                  2879     200000         531
ORDERS_DATE_IX                  200000     200000         531
ORDERS_CUSTOMER_IX              200000     200000         418

表のブロック数（1000）と行数（200,000）を目安にして読む。

  • ブロック数に近い → 索引の順に並べると行がまとまっている（主キー SYS_C008729: 960）。order_id の順に行を挿入したためである
  • 行数に近い → 索引の順に 1 行進むたびに別のブロックへ飛ぶ（ORDERS_DATE_IX と ORDERS_CUSTOMER_IX: 200,000）。連続した受注は日付も顧客もばらばらなためである
  • ORDERS_STATUS_IX の 2879 は、ブロック数の約 3 倍である。値ごとに見ると、行は表の順に並んでいる。しかし 3 種類の値のそれぞれが、表全体にわたって散らばっている。そのため、値 1 つにつき表をほぼ一周する

クラスタリング・ファクタはオプティマイザも Cost の計算に使う。値が行数に近い索引ほど、表を引く Cost が高く見積もられる。

E-Rows が 66667 になっている理由

F1〜G2 の E-Rows は、すべて 66667 である。1 章と同じで、status にヒストグラムがないため、オプティマイザは 3 種類の値が均等に分布していると仮定している（200,000 ÷ 3）。そのため、オプティマイザは SHIPPED（実際は 196,000 行）と PENDING（実際は 3,000 行）を区別できていない。これは 6 章で扱う。

まとめ

  • アクセスパスは計画の葉に現れる。Buffers の大半は葉で発生する
  • INDEX UNIQUE SCAN は 1 行を、INDEX RANGE SCAN は範囲を引く。TABLE ACCESS BY INDEX ROWID で表の行を読む
  • TABLE ACCESS FULL の条件は filter で、全件を読んでから捨てる
  • 必要な列がすべて索引にあれば、表を読まずに済む（INDEX RANGE SCAN だけの計画、INDEX FAST FULL SCAN）
  • INDEX FULL SCAN (MIN/MAX) は、索引の端だけを読む
  • 索引が効くかどうかは、取り出す行の割合と、その行のまとまり具合（CLUSTERING_FACTOR）で決まる。行が散らばっていれば、少ない行数でも表のほぼ全ブロックを読むことになる
  • 行がまとまるかどうかは、INSERT の順番で決まる。INSERT の順番と値の順番が一致する列では行がまとまり、一致しない列では散らばる
  • 行が散らばっていると、索引の Buffers は取る件数に比例して増え、FULL は一定である。FULL はまとめて読めるので、Buffers が索引より多くても FULL が選ばれることがある
  • RANGE SCAN が有効かどうかは、実測では「表アクセスの Buffers」と「索引の A-Rows と表アクセスの A-Rows の差」で判断する。実行前には、CLUSTERING_FACTOR × 取り出す割合 を表のブロック数と比べて見積もる
