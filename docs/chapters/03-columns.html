題材の SQL

関西の顧客の受注について、明細の行数を数える。内側が何度も実行される様子を見るため、ヒントで結合方式を NESTED LOOPS に固定している。スクリプトは sql/ch03_columns.sql にある。

SELECT /*+ GATHER_PLAN_STATISTICS LEADING(c o i) USE_NL(o) USE_NL(i) */
       COUNT(*) AS item_cnt
FROM   customers c
JOIN   orders o       ON o.customer_id = c.customer_id
JOIN   order_items i  ON i.order_id    = o.order_id
WHERE  c.region = 'KANSAI';

Starts — その操作を実行した回数

NESTED LOOPS は、外側（第 1 子）の 1 行ごとに内側（第 2 子）を 1 回実行する。そのため、内側の Starts は外側の行数と同じになる。

内側の操作 Starts 外側の行数
Id 5・6（ORDERS を顧客ごとに引く） 2,000 Id 4 の A-Rows = 2,000（関西の顧客）
Id 7（明細を受注ごとに引く） 40,000 Id 3 の A-Rows = 40,000（その受注）

Starts が大きい行は、1 回あたりの処理が軽くても合計で重くなりやすい。

E-Rows と A-Rows — 1 回あたりと合計

小さな例: 顧客 3 人

まず顧客を 3 人に絞り、同じ形の計画を見る。

SELECT /*+ GATHER_PLAN_STATISTICS LEADING(c o) USE_NL(o) INDEX(o orders_customer_ix) FULL(c) */
       MAX(c.name), COUNT(o.amount)
FROM   customers c
JOIN   orders o ON o.customer_id = c.customer_id
WHERE  c.customer_id IN (1, 6, 11);

---------------------------------------------------------------------------------------------
| Id  | Operation           | Name               | Starts | E-Rows | A-Rows |   A-Time   | Buffers |
---------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT    |                    |      1 |        |      1 |00:00:00.01 |      65 |
|   1 |  SORT AGGREGATE     |                    |      1 |      1 |      1 |00:00:00.01 |      65 |
|   2 |   NESTED LOOPS      |                    |      1 |     60 |     60 |00:00:00.01 |      65 |
|*  3 |    TABLE ACCESS FULL| CUSTOMERS          |      1 |      3 |      3 |00:00:00.01 |      60 |
|*  4 |    INDEX RANGE SCAN | ORDERS_CUSTOMER_IX |      3 |     20 |     60 |00:00:00.01 |       5 |
---------------------------------------------------------------------------------------------

Id 4 は 1 回だけ動くのではない。上から顧客が 1 人来るたびに 1 回動くので、3 回動いている。

回 上から来た顧客 見積り（1 回あたり） 実際
1 回目 顧客 1 20 20
2 回目 顧客 6 20 20
3 回目 顧客 11 20 20
計画の表示 Starts = 3 E-Rows = 20 A-Rows = 60

計画の 1 行は、複数回の実行をまとめて表示している。E-Rows は 1 回分、A-Rows は合計である。件数が 20 から 60 に増えたのではなく、1 回分の数字と 3 回分の合計が同じ行に並んでいるだけである。

c.name を SELECT する理由

c.name を SELECT しないと、customers の列を使わないため結合除去が起き、別の形の計画になる（2 章を参照）。

2000 人の例

2 つの列は単位が違う。

  • E-Rows：1 回の実行あたりの見積り行数
  • A-Rows：全実行の合計の実績行数

そのため、見積りが正しかったかどうかは E-Rows × Starts と A-Rows を比べて判断する。

Id E-Rows Starts E-Rows × Starts A-Rows 判定
4 2,000 1 2,000 2,000 正確
5 20 2,000 40,000 40,000 正確
7 2 40,000 80,000 80,001 ほぼ正確

Id 5 の E-Rows 20 と A-Rows 40,000 だけを並べると、見積りが 2,000 倍外れたように見える。しかし実際は、見積りは正確である。

1 章の補足

1 章では「E-Rows と A-Rows が大きくずれている行を探す」と書いた。Starts が 1 の行はそのまま比べてよい。 Starts が 2 以上の行では、E-Rows に Starts を掛けてから比べる。

A-Rows を読み違える場合

A-Rows は実際に数えた値なので、数え間違いはない。ただし「何を数えた値か」を取り違えると読み間違える。

1. 行を最後まで取り出さなかった

SQL Developer などの画面ツールは、最初の数十行だけを取り出して表示することが多い。このとき、A-Rows は取り出した分だけになる。

次は、受注と顧客を結合する SQL を実行し、最初の 50 行だけを取り出して閉じたときの計画である（sql/ch03_columns.sql の後半）。

SQL_ID  ccmwp2ub9nuk4, child number 0

---------------------------------------------------------------------------------------------------------------------
| Id  | Operation          | Name      | Starts | E-Rows | A-Rows |   A-Time   | Buffers |  OMem |  1Mem | Used-Mem |
---------------------------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT   |           |      1 |        |     50 |00:00:00.01 |     112 |       |       |          |
|*  1 |  HASH JOIN         |           |      1 |    200K|     50 |00:00:00.01 |     112 |  1810K|  1810K| 2555K (0)|
|   2 |   TABLE ACCESS FULL| CUSTOMERS |      1 |  10000 |  10000 |00:00:00.01 |      60 |       |       |          |
|   3 |   TABLE ACCESS FULL| ORDERS    |      1 |    200K|     50 |00:00:00.01 |      52 |       |       |          |
---------------------------------------------------------------------------------------------------------------------

ORDERS の E-Rows は 200K だが、A-Rows は 50 しかない。見積りが外れたのではない。50 行を返したところで取り出しが止まり、ORDERS もそこで読むのをやめただけである。

調査では、SQL*Plus などで全件を取り出してから計画を表示する。または、SELECT COUNT(*) FROM (...) のように件数を数える SQL に包んで実行する。

部分的に読んだ表と、全部読んだ表

HASH JOIN の第 1 子（CUSTOMERS）は、ハッシュ表を作るために最初に全件を読む。そのため 10000 行のままである。 途中で止まったのは、第 2 子（ORDERS）の読み込みだけである。

2. A-Rows は全実行の合計である

前の節のとおり、A-Rows は Starts 回分の合計である。E-Rows と直接比べず、E-Rows × Starts と比べる。

3. 'ALLSTATS LAST' は最後の 1 回だけ

'ALLSTATS LAST' は、最後に実行した 1 回分の実績を表示する。バインド変数の値が変われば、A-Rows も変わる。別の値で遅くなっている場合は、その値で実行してから表示する。

LAST を付けずに 'ALLSTATS' と指定すると、そのカーソルのこれまでの全実行の累計を表示する。

4. A-Time には誤差がある

GATHER_PLAN_STATISTICS で実績を集めると、計測そのものに負荷がかかる。行数の多い操作ほど、A-Time が実際より長く出やすい。値の丸めもある。行数ではなく時間で比べるときは、この誤差に注意する。

Buffers — 子の分を含む累計

Buffers は読んだブロックの数（論理読み込み）である。この値は子の操作の分を含む累計になっている。操作そのものが読んだ量は、次の式で求める。

自分の分 = 自分の Buffers − 子の Buffers の合計
Id 操作 Buffers（累計） 子の合計 自分の分
7 INDEX RANGE SCAN ORDER_ITEMS_PK 80,235 —（子なし） 80,235
6 INDEX RANGE SCAN ORDERS_CUSTOMER_IX 2,413 —（子なし） 2,413
5 TABLE ACCESS BY INDEX ROWID BATCHED ORDERS 42,413 2,413（Id 6） 40,000
4 TABLE ACCESS FULL CUSTOMERS 60 —（子なし） 60
3 NESTED LOOPS 42,473 60 + 42,413 = 42,473 0
2 NESTED LOOPS 122K 42,473 + 80,235 = 122,708 ≒ 0

K 表記は丸められている

大きな値は 122K のように丸めて表示される。Id 2 は 122,708 前後と考えられるが、正確な値は分からない。 自分の分を引き算で求めるときは、誤差が出ることを前提にする。

どこで読んでいるか

自分の分が最も大きいのは Id 7（80,235）である。1 回あたりでは 80,235 ÷ 40,000 ≒ 2 ブロックしか読んでいない。それでも 4 万回実行しているので、積み上がって最大になった。

次に大きいのは Id 5（40,000）で、受注 1 行あたり約 1 ブロックを読んでいる。1 人の顧客の受注は表の中のあちこちに散らばっている。そのため、1 行を取るたびに別のブロックを読むことになる。

NESTED LOOPS の行（Id 2・3）は、子から受け取った行を組み合わせるだけで、自分ではブロックを読まない。

A-Time — これも累計で、誤差がある

A-Time も子の分を含む累計である。ただし計測は丸められており、誤差も含む。この計画でも、Id 3 の 0.39 秒が親の Id 2 の 0.38 秒を上回っている。累計として考えればありえない値である。

時間は計測のぶれも受けやすい。どの操作が重いかを比べるときは、時間より Buffers を使うほうが確実である。

HASH JOIN 版は、ORDERS（20 万行）と ORDER_ITEMS（40 万行）を全件 FULL で読んでいる。それでも、読んだブロック数は NESTED LOOPS 版の約 1/56 である。

FULL SCAN は、表のブロックを先頭から 1 回ずつ読むだけで済む。それに対して索引を何万回も引くと、同じブロックを何度も読むことになる。そのため、全件を読むほうが軽いことがある。

「索引を使えば速い」とは限らない。結合方式をどう選ぶかは 5 章で扱う。

Cost — オプティマイザの見積りコスト

ALLSTATS LAST では表示されないが、EXPLAIN PLAN の出力には Cost 列がある。同じ 2 つの SQL を EXPLAIN PLAN にかけ、DBMS_XPLAN.DISPLAY(NULL, NULL, 'BASIC +ROWS +COST') で表示した。

EXPLAIN PLAN FOR
SELECT /*+ LEADING(c o i) USE_NL(o) USE_NL(i) */ COUNT(*) ... ;   -- NESTED LOOPS 版

Cost の意味

  • Cost は、実行前に見積もった資源量である。おおむね「単一ブロック読み込み何回分か」という単位で表される。実測値ではない
  • オプティマイザは、候補の計画のうち Cost が最小のものを選ぶ。ヒントなしで HASH JOIN 版（987）が選ばれたのは、NESTED LOOPS 版（122K）より小さいからである

Cost も累計である

Cost も子の分を含む累計である。さらに NESTED LOOPS の内側の行（Id 5・7）では、Rows と同じく Cost も 1 回あたりの値になる。親の Cost は、外側の行数を掛けて積み上がる。

Id 3:  2000 回 × 21（Id 5 の 1 回あたり） ≒ 42027
Id 2:  42027 + 40000 回 × 2（Id 7 の 1 回あたり） ≒ 122K

この 122K は、実測した Buffers の 122K とほぼ一致している。見積り行数が正確なので、コストの見積りも実態に近い。

Cost を見るときの注意

  • 別の SQL どうしで Cost を比べても意味がない。Cost は、同じ SQL の候補の計画を比べるための値である
  • 見積り行数が外れれば、Cost も外れる。1 章の例では E-Rows 66,667 に対して A-Rows は 3,000 だった。この場合、Cost はずれた行数をもとに計算されている
  • そのため調査では、Cost ではなく A-Rows と Buffers を見る

OMem / 1Mem / Used-Mem — 作業用メモリ

ハッシュ表やソートが使ったメモリを表す列である。

  • OMem：すべてをメモリ内で処理するのに必要な量の見積り
  • 1Mem：ディスクへの 1 回の書き出しで済ませる場合に必要な量の見積り
  • Used-Mem：実際に使った量

Used-Mem の後ろの括弧の数字は、ディスクに書き出した回数である。(0) なら、ディスクを使わずメモリだけで処理できている。

まとめ

  • Starts はその操作を実行した回数である。NESTED LOOPS の内側は、外側の行数と同じ回数だけ実行される
  • E-Rows は 1 回あたり、A-Rows は合計である。見積りの当否は E-Rows × Starts と A-Rows を比べて判断する
  • Buffers と A-Time は子の分を含む累計である。操作そのものの分は「自分 − 子の合計」で求める
  • 重い操作を探すときは、時間より Buffers を見る。1 回あたりは軽くても、Starts が大きいと積み上がる
  • 索引を何万回も引くより、FULL SCAN で全件を読むほうが軽いことがある
  • Cost は実行前の見積りで、オプティマイザが計画を選ぶための値である。調査では Cost より A-Rows と Buffers を見る
  • A-Rows は実測だが、行を最後まで取り出さないと少なく出る。調査では全件を取り出してから計画を見る
