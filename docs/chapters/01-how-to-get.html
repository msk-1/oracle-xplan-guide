実行計画の取り方は大きく 2 つある。実行せずに予定を見る方法と、実行して実績と並べて見る方法である。調査では後者を基本にする。

題材の SQL

PENDING の受注を顧客の地域ごとに集計する。スクリプトは sql/ch01_explain_vs_cursor.sql にある。

SELECT c.region, COUNT(*) AS cnt, SUM(o.amount) AS total
FROM   orders o
JOIN   customers c ON c.customer_id = o.customer_id
WHERE  o.status = 'PENDING'
GROUP  BY c.region;

方法 2: DISPLAY_CURSOR — 実行した「実績」

SET SERVEROUTPUT OFF

SELECT /*+ GATHER_PLAN_STATISTICS */ ... ;     -- 上の SQL を実行する

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

Plan hash value: 1819830487

----------------------------------------------------------------------------------------------------------------------
| Id  | Operation           | Name      | Starts | E-Rows | A-Rows |   A-Time   | Buffers |  OMem |  1Mem | Used-Mem |
----------------------------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT    |           |      1 |        |      3 |00:00:00.01 |    1064 |       |       |          |
|   1 |  HASH GROUP BY      |           |      1 |      5 |      3 |00:00:00.01 |    1064 |  1088K|  1088K|          |
|*  2 |   HASH JOIN         |           |      1 |  66667 |   3000 |00:00:00.01 |    1064 |  1947K|  1947K| 1986K (0)|
|   3 |    TABLE ACCESS FULL| CUSTOMERS |      1 |  10000 |  10000 |00:00:00.01 |      60 |       |       |          |

方法 1 の Rows は、ここでは E-Rows（Estimated Rows）になる。加えて実績の列が並ぶ。

列 意味
Starts その操作が実行された回数
E-Rows 見積り行数（1 回の実行あたり）
A-Rows 実際に返した行数（全実行の合計）
A-Time 実際にかかった時間（子の操作を含む累計）
Buffers 読んだブロック数（論理読み込み、子を含む累計）

各列の詳しい読み方は 3 章で扱う。

手順の要点

  • GATHER_PLAN_STATISTICS ヒントがないと、A-Rows などの実績列は表示されない
  • 'ALLSTATS LAST' は「直前の 1 回の実行の実績」を表示する指定である
  • DISPLAY_CURSOR(NULL, NULL, ...) は、同じセッションで直前に実行した SQL の計画を表示する

SERVEROUTPUT を OFF にする

SQL*Plus で SERVEROUTPUT が ON だと、問い合わせの後に DBMS_OUTPUT の呼び出しが自動で実行される。 すると「直前の SQL」がそれに置き換わり、目的の計画を表示できない。

予定と実績を比べて分かること

ORDERS の行（Id 4）で、見積りと実績が大きくずれている。

行数
見積り（E-Rows） 66,667
実績（A-Rows） 3,000

見積りが約 22 倍多い。方法 1 だけを見ていると、このずれに気づけない。

なぜ 66,667 なのか

status 列の統計を見る。

SELECT column_name, num_distinct, density, histogram
FROM   user_tab_col_statistics
WHERE  table_name = 'ORDERS' AND column_name = 'STATUS';

COLUMN_NAME  NUM_DISTINCT    DENSITY HISTOGRAM
------------ ------------ ---------- ---------------
STATUS                  3 .333333333 NONE

ヒストグラムがない（NONE）。この場合、オプティマイザは値が均等に分布していると仮定し、等価条件の選択率を 1 / 異なり値の数 とする。

200,000 行 × 1/3 ≒ 66,667 行

実際の分布は SHIPPED 196,000 / PENDING 3,000 / CANCELLED 1,000 と大きく偏っている。そのため、見積りが外れた。

この SQL は小さいので、見積りが外れても計画は変わらず、実行も一瞬で終わる。しかし大きな SQL では、見積りのずれが結合方式や結合順の選び間違いにつながる。対策（ヒストグラム）は 6 章で扱う。

まとめ

  • EXPLAIN PLAN は予定である。実行しないので、実績は出ない
  • 調査には GATHER_PLAN_STATISTICS + DISPLAY_CURSOR(..., 'ALLSTATS LAST') を使う
  • 実行計画を読むときは、まず E-Rows と A-Rows が大きくずれている行を探す
  • ヒストグラムがない列では、値が均等に分布すると仮定して見積もられる
