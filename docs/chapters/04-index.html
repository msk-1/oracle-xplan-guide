1. 前提: ブロックと ROWID

ブロック

Oracle は表のデータをブロックという単位で保存し、ブロック単位で読み書きする。ORDERS は 1000 ブロックに 20 万行が入っており、1 ブロックあたり約 200 行である。

計画の Buffers は読んだブロック数である。1 行だけ欲しくても、その行が入っているブロックを丸ごと 1 つ読む。

    BLOCKS   NUM_ROWS
---------- ----------
      1000     200000

ROWID

ROWID は行の住所である。どのファイルの、どのブロックの、何番目の行かを表す。

SELECT order_id, rowid, DBMS_ROWID.ROWID_BLOCK_NUMBER(rowid) AS block_no
FROM   orders
WHERE  order_id IN (12345, 12346);

  ORDER_ID ROWID                BLOCK_NO
---------- ------------------ ----------
     12345 AAAR6IAAYAAAADhACt        225
     12346 AAAR6IAAYAAAADhACu        225

受注 12345 と 12346 は、どちらも 225 番のブロックに入っている。ROWID が分かれば、表のどこを読めばよいかが 1 回で決まる。

2. 索引の構造 — B-tree

索引は「値 → ROWID」の対応表

索引は、列の値と ROWID の組を、値の順に並べて保存したものである。本の巻末索引と同じく、「order_id 12345 は 225 番ブロックにある」と引ける。

索引の 1 項目（エントリ）は次の形をしている。

キー（列の値） ROWID（行の住所）
12345 AAAR6IAAYAAAADhACt

索引には、索引に含めた列の値しか入っていない。それ以外の列（ORDERS なら order_date や amount）が必要なときは、ROWID を使って表を読みに行く。

木の形

項目は葉ブロックに値の順で詰められる。葉を探すための目次がルートとブランチである。葉どうしは左右の隣とつながっていて、値の順にたどれる。

部品 役割 辞典にたとえると
ルート 最初に読むブロック。どのブランチ（または葉）に進むかが書いてある 背の「つめ」（あ・か・さ…）
ブランチ 目次の目次。葉が多くてルートに書ききれないときに入る —
葉 値と ROWID の組が、値の順に並んでいる 開いたページ
表のブロック 実際の行 説明の本文

木の段数は USER_INDEXES.BLEVEL で確かめる。BLEVEL は「ルートから葉までの段数 − 1」である。

SELECT index_name, blevel, leaf_blocks, num_rows
FROM   user_indexes
WHERE  table_name = 'ORDERS'
ORDER  BY index_name;

INDEX_NAME               BLEVEL LEAF_BLOCKS   NUM_ROWS
-------------------- ---------- ----------- ----------
ORDERS_CUSTOMER_IX            1         418     200000
ORDERS_DATE_IX                2         531     200000
ORDERS_STATUS_IX              2         531     200000
SYS_C008729                   1         374     200000

主キー索引 SYS_C008729（BLEVEL 1）はルートと葉の 2 段、ORDERS_DATE_IX（BLEVEL 2）はルート・ブランチ・葉の 3 段である。

ルートブロックの中身

ルートには、葉ごとの区切り（キーの範囲 → 葉ブロック）が書いてある。主キー索引は葉が 374 個あり、葉 1 個あたり約 535 件が入る。

ルートに書いてある区切り 進む先
order_id 1 〜 535 葉 1
order_id 536 〜 1070 葉 2
… …
order_id 12306 〜 12840 葉 24 ← 12345 はここ
… …
order_id … 〜 200000 葉 374

区切りの数値は、平均の件数から計算した説明用の値であり、実際のブロックの区切りとは異なる。

1 行を引く: INDEX UNIQUE SCAN の経路

order_id = 12345 を引くときに通る経路を図にする。色の付いた枠が実際に読んだブロックである。

| Id  | Operation                   | Name        | Starts | E-Rows | A-Rows | Buffers |
|   0 | SELECT STATEMENT            |             |      1 |        |      1 |       3 |
|   1 |  TABLE ACCESS BY INDEX ROWID| ORDERS      |      1 |      1 |      1 |       3 |
|*  2 |   INDEX UNIQUE SCAN         | SYS_C008729 |      1 |      1 |      1 |       2 |
読んだブロック 中身 計画の行
1 ブロック目 索引のルート Id 2（索引の Buffers 2）
2 ブロック目 索引の葉 24 Id 2
3 ブロック目 表のブロック 225 Id 1（3 − 2 = 1）

索引の段数と、表を読む手間は別である

索引をたどって分かるのは行の住所（ROWID）までである。 索引の段数は「住所を調べる手間」、表のブロックを読むのは「その家を訪ねる手間」であり、別々にかかる。

複数の行を引く: INDEX RANGE SCAN の経路

範囲の条件（BETWEEN や >=）や重複のある値では、最初の葉にたどり着いた後、隣の葉へ横に読み進める。条件に合わない値が出てきたところで止まる。

order_date BETWEEN 3/1 AND 3/2 を引く場合の経路を図にする。色の付いた枠と太線が実際に読んだ部分である。

索引の部分は、段数 + 横に読んだ葉の枚数で済む。表の部分は、ROWID が指すブロックの数だけ読む。同じ値の行が表の中で散らばっていれば、表を読むブロックは行数と同じだけ増える（4-2 の「同じ日付の行はどこにあるか」を参照）。

3. 件数が増えても検索が遅くならない理由

目次が大きくなったら、1 ブロックに詰め込むのではなく段を増やす。1 ブロック（標準 8KB）に区切りが約 500 個入るとした場合の概算は次のとおりである。

段数 扱える件数の目安 1 行を探すのに読む索引ブロック
2 段（ルート → 葉） 約 25 万件 2
3 段（ルート → ブランチ → 葉） 約 1 億件 3
4 段 約 600 億件 4

キーの長さによって大きく変わるため、目安として扱う。件数が 400 倍になっても、読むブロックは 1 つしか増えない。

ブロックの中の項目は値の順に並んでいるので、二分探索で探せる。区切りが 500 個あっても 9 回ほどの比較で済み、しかもメモリ上の処理である。したがって、検索の手間はおおむね段数 = 読むブロック数で決まる。

段数の上限

段を持つのは索引の木であり、ブロックではない。実務では 2〜4 段（BLEVEL 1〜3）がほとんどである。

上限は公式ドキュメントに明記されていない。Oracle-L の議論では、22〜24 段あたりという非公式の報告がある（Oracle-L, 2004）。実務で上限に達することはまずない。BLEVEL が件数から予想されるより大きい場合は、長すぎるキーを疑う。

4. ブロックの中は並んでいるか

索引と表で異なる。

ブロック 中身の順番
索引ブロック キーの順に並んでいる。新しい値は正しい位置に差し込まれる。だから二分探索ができる
表ブロック（通常のヒープ表） 並んでいない。空きのあるブロックに、空いている場所から行を入れる

ORDERS が受注番号の順に入っているように見えるのは、作成時に番号順で一括 INSERT したからにすぎない。DELETE で空いた場所に別の行が入ったり、UPDATE で行が伸びて移動したりすると、順番は崩れる。

ORDER BY のない SELECT の順番は保証されない

表から返る行の順番は、ブロック内の置き場所や実行計画によって変わる。 順番が必要なら、必ず ORDER BY を書く。

行を特定の列の順に並べて保存したい場合は、次の方法がある。

方法 内容 注意
索引構成表（IOT） 表そのものを主キー順の B-tree として保存する 主キー以外の列での検索には二次索引が要る
並べて作り直す CREATE TABLE ... AS SELECT ... ORDER BY や ALTER TABLE ... MOVE で、ある列の順に入れ直す その後の DML で再び崩れていく

どちらの方法でも、並べ替えの基準にできる列は 1 つ（1 組）だけである。受注番号の順に並べれば日付の順にはならない。

まとまり具合を決めるのは INSERT の順番

ある列で引いたときに表の行がまとまっているかは、INSERT した順番とその列の値の順番が一致しているかで決まる。

列 INSERT の順番との関係 1 ブロックの中身 CLUSTERING_FACTOR
受注番号 INSERT の順番と同じ順に増える 連続した番号が約 200 件 960（≒ 表のブロック数）
日付 1 件ごとに次の日へ進み、1000 件で循環する 200 件すべて違う日付 200,000（＝ 行数）

CLUSTERING_FACTOR は、索引の順に全行をたどったときに表のブロックを何回切り替えるかの数である。表のブロック数に近いほど行がまとまっており、行数に近いほど散らばっている。

5. 複合索引

複合索引の並び方

複数の列をまとめた索引を複合索引という。項目は1 列目の順に並び、1 列目が同じ値の中で 2 列目の順に並ぶ。電話帳が「姓 → 名」の順に並んでいるのと同じである。

(order_date, amount) の索引の葉は、次のように並ぶ（値は説明用の作例）。

 order_date   amount   ROWID
 ──────────  ───────  ──────
 2024-02-29    48500   …
 2024-03-01      500   …   ┐
 2024-03-01    13000   …   │ 3/1 の中は amount の順
 2024-03-01    49500   …   │
 2024-03-01    49900   …   ┘
 2024-03-02     1300   …   ┐
 2024-03-02    49100   …   │ 3/2 の中も amount の順
 2024-03-02    49700   …   ┘
 2024-03-03      800   …

amount だけを見ると、索引全体では順番に並んでいない（49900 の次に 1300 が来る）。2 列目以降は、前の列の値が同じ範囲の中でしか並んでいない。 この性質から、複合索引のすべての規則が導かれる。

効果 1: 表を読む前に絞り込める

「3/1〜3/2 の受注のうち、金額が 49000 より大きいもの」を取り出す。まず単一列の索引 (order_date) で実行する。

| Id  | Operation                            | Name           | Starts | E-Rows | A-Rows |   A-Time   | Buffers |
|   0 | SELECT STATEMENT                     |                |      1 |        |      1 |00:00:00.01 |     404 |
|   1 |  SORT AGGREGATE                      |                |      1 |      1 |      1 |00:00:00.01 |     404 |
|*  2 |   TABLE ACCESS BY INDEX ROWID BATCHED| ORDERS         |      1 |     18 |     16 |00:00:00.01 |     404 |
|*  3 |    INDEX RANGE SCAN                  | ORDERS_DATE_IX |      1 |    600 |    400 |00:00:00.01 |       4 |

Predicate Information (identified by operation id):
---------------------------------------------------

   2 - filter("AMOUNT">49000)
   3 - access("ORDER_DATE">=TO_DATE(' 2024-03-01 00:00:00', 'syyyy-mm-dd hh24:mi:ss') AND
              "ORDER_DATE"<=TO_DATE(' 2024-03-02 00:00:00', 'syyyy-mm-dd hh24:mi:ss'))

索引には amount が入っていないので、日付が合う 400 件すべてについて表を読み、表で amount を見て 384 件を捨てている。

次に、複合索引 (order_date, amount) を作って同じ SQL を実行する。

CREATE INDEX orders_date_amount_ix ON orders (order_date, amount);

| Id  | Operation         | Name                  | Starts | E-Rows | A-Rows |   A-Time   | Buffers | Reads  |
|   0 | SELECT STATEMENT  |                       |      1 |        |      1 |00:00:00.01 |       4 |      3 |
|   1 |  SORT AGGREGATE   |                       |      1 |      1 |      1 |00:00:00.01 |       4 |      3 |
|*  2 |   INDEX RANGE SCAN| ORDERS_DATE_AMOUNT_IX |      1 |     18 |     16 |00:00:00.01 |       4 |      3 |

Predicate Information (identified by operation id):
---------------------------------------------------

   2 - access("ORDER_DATE">=TO_DATE(' 2024-03-01 00:00:00', 'syyyy-mm-dd hh24:mi:ss') AND
              "AMOUNT">49000 AND "ORDER_DATE"<=TO_DATE(' 2024-03-02 00:00:00', 'syyyy-mm-dd hh24:mi:ss'))
       filter("AMOUNT">49000)

Reads は、メモリになかったためディスクから読んだブロック数である。索引を作った直後なので現れている。

索引 表を読んだブロック 合計 Buffers
(order_date) 400 404
(order_date, amount) 0 4

この例では、SELECT が SUM(amount) だけで、必要な列がすべて索引に入っている。そのため表を一度も読まずに済んだ（TABLE ACCESS の行がない）。

効果 2: 索引だけで答えを出す（カバリング）

索引にない列（status）も SELECT すると、表を読む行が復活する。

| Id  | Operation                            | Name                  | Starts | E-Rows | A-Rows |   A-Time   | Buffers |
|   0 | SELECT STATEMENT                     |                       |      1 |        |      1 |00:00:00.01 |      20 |
|   1 |  SORT AGGREGATE                      |                       |      1 |      1 |      1 |00:00:00.01 |      20 |
|   2 |   TABLE ACCESS BY INDEX ROWID BATCHED| ORDERS                |      1 |     18 |     16 |00:00:00.01 |      20 |
|*  3 |    INDEX RANGE SCAN                  | ORDERS_DATE_AMOUNT_IX |      1 |     18 |     16 |00:00:00.01 |       4 |

それでも、表を読むのは絞り込んだ後の 16 件だけなので、合計は 20 ブロックで済む。

SELECT する列 表を読むか Buffers
索引の列だけ（SUM(amount)） 読まない 4
索引にない列も（MAX(status)） 絞り込んだ 16 件だけ読む 20

必要な列をすべて含む索引をカバリング索引と呼ぶ。列を足すほど索引は大きくなるので、よく実行される SQL に絞って使う。

列の順番 1: 先頭列の条件がないと RANGE SCAN できない

(order_date, amount) の索引に対して、2 列目の amount だけで検索する。

SELECT COUNT(*) FROM orders WHERE amount = 25500;

| Id  | Operation             | Name                  | Starts | E-Rows | A-Rows |   A-Time   | Buffers | Reads  |
|   0 | SELECT STATEMENT      |                       |      1 |        |      1 |00:00:00.03 |     676 |    664 |
|   1 |  SORT AGGREGATE       |                       |      1 |      1 |      1 |00:00:00.03 |     676 |    664 |
|*  2 |   INDEX FAST FULL SCAN| ORDERS_DATE_AMOUNT_IX |      1 |      4 |      4 |00:00:00.01 |     676 |    664 |

Predicate Information (identified by operation id):
---------------------------------------------------

   2 - filter("AMOUNT"=25500)

述語が access ではなく filter になっている。amount = 25500 の項目は、索引のあちこちの日付の中に散らばっている（上の並び方の図を参照）。そのため木をたどって 1 か所に降りることができず、索引を全部読んで（676 ブロック）ふるいにかけている。

電話帳で「名が『太郎』の人」を探すのと同じである。姓が分からなければ、全ページを見るしかない。

INDEX SKIP SCAN

先頭列の値の種類が少ない場合、オプティマイザは先頭列の値ごとに木を降りる INDEX SKIP SCAN を選ぶことがある。 この例では先頭列（日付）が 1000 種類あるため選ばれていない。

列の順番 2: 等価条件の列を先、範囲条件の列を後

「顧客 42 の、2024 年以降の受注」を数える。条件は等価（customer_id = 42）と範囲（order_date >= …）の組である。列の順番だけが違う 2 つの索引で比べる。

CREATE INDEX orders_cust_date_ix ON orders (customer_id, order_date);
CREATE INDEX orders_date_cust_ix ON orders (order_date, customer_id);

SELECT COUNT(*) FROM orders
WHERE  customer_id = 42 AND order_date >= DATE '2024-01-01';

(customer_id, order_date) — 等価の列が先

| Id  | Operation         | Name                | Starts | E-Rows | A-Rows |   A-Time   | Buffers |
|   0 | SELECT STATEMENT  |                     |      1 |        |      1 |00:00:00.01 |       3 |
|   1 |  SORT AGGREGATE   |                     |      1 |      1 |      1 |00:00:00.01 |       3 |
|*  2 |   INDEX RANGE SCAN| ORDERS_CUST_DATE_IX |      1 |     13 |     20 |00:00:00.01 |       3 |

Predicate Information (identified by operation id):
---------------------------------------------------

   2 - access("CUSTOMER_ID"=42 AND "ORDER_DATE">=TO_DATE(' 2024-01-01 00:00:00',
              'syyyy-mm-dd hh24:mi:ss'))

(order_date, customer_id) — 範囲の列が先

| Id  | Operation         | Name                | Starts | E-Rows | A-Rows |   A-Time   | Buffers | Reads  |
|   0 | SELECT STATEMENT  |                     |      1 |        |      1 |00:00:00.01 |     412 |    410 |
|   1 |  SORT AGGREGATE   |                     |      1 |      1 |      1 |00:00:00.01 |     412 |    410 |
|*  2 |   INDEX RANGE SCAN| ORDERS_DATE_CUST_IX |      1 |     13 |     20 |00:00:00.01 |     412 |    410 |

Predicate Information (identified by operation id):
---------------------------------------------------

   2 - access("ORDER_DATE">=TO_DATE(' 2024-01-01 00:00:00', 'syyyy-mm-dd hh24:mi:ss') AND
              "CUSTOMER_ID"=42)
       filter("CUSTOMER_ID"=42)

結果はどちらも 20 件だが、読んだブロックは 3 と 412 で、100 倍以上違う。葉の並び方を描くと理由が分かる（値は説明用の作例）。

  • 等価の列が先の場合、customer_id = 42 の項目は 1 か所に固まっている。その中は日付順なので、2024-01-01 の位置に降りて、42 が終わるまで読めばよい。
  • 範囲の列が先の場合、2024-01-01 以降の項目は、日付ごとに全顧客分が並ぶ。顧客 42 の項目は 1 日に 1 件ずつ飛び飛びにしかないので、範囲全体（2024-01-01〜最終日の 635 日 × 200 件 ≒ 12.7 万項目、約 410 ブロック）を読んでふるいにかけるしかない。

Predicate Information にもこの違いが出ている。範囲が先の索引では、CUSTOMER_ID=42 が access だけでなく filter にも現れる。木を降りる位置を決めるのには日付しか使えず、顧客の条件は読んだ項目をふるいにかけるのに使われている、という意味である。

規則

複合索引の列は 等価条件（=）の列を先、範囲条件（>=, BETWEEN, LIKE 'abc%'）の列を後 に並べる。 範囲条件の列より後ろの列は、読む範囲を狭めるのには使えず、ふるいにかけるのにしか使えない。

測り終えたら索引を削除し、スキーマを元に戻す（sql/ch04_composite_index.sql の末尾で行う）。

6. 索引があっても RANGE SCAN できない書き方

索引は「列の値そのもの」の順に並んでいる。列を加工すると、その順番が使えなくなる。

列に関数をかける（実測）

2024 年 3 月の受注を TRUNC で書いた場合と、範囲で書いた場合を比べる（(order_date, amount) の索引がある状態で測った）。

-- 列に関数をかける
WHERE TRUNC(order_date, 'MM') = DATE '2024-03-01'
-- 同じ意味を範囲で書く
WHERE order_date >= DATE '2024-03-01' AND order_date < DATE '2024-04-01'

TRUNC で書いた場合
| Id  | Operation             | Name                  | Starts | E-Rows | A-Rows |   A-Time   | Buffers |
|*  2 |   INDEX FAST FULL SCAN| ORDERS_DATE_AMOUNT_IX |      1 |   2000 |   6200 |00:00:00.02 |     676 |

   2 - filter(TRUNC(INTERNAL_FUNCTION("ORDER_DATE"),'fmmm')=TO_DATE(' 2024-03-01 00:00:00',
              'syyyy-mm-dd hh24:mi:ss'))

範囲で書いた場合

書き方 操作 Buffers
TRUNC(order_date, 'MM') = … INDEX FAST FULL SCAN（全部読んでふるい） 676
order_date >= … AND order_date < … INDEX RANGE SCAN 23

索引に入っているのは order_date の値であり、TRUNC(order_date, 'MM') の値ではない。そのため木を降りる位置を決められない。関数の結果で探す必要があるなら、関数の式そのものに索引を作る（ファンクション索引）。

TRUNC 版では見積りも外れている（E-Rows 2000 に対して A-Rows 6200）。関数をかけた列には統計がないので、オプティマイザが決め打ちの選択率で見積もるためである。

文字列の列と数値を比べる WHERE code = 123 暗黙の型変換で TO_NUMBER(code) = 123 になり、列に関数がかかる WHERE code = '123'
前方が不定の LIKE WHERE name LIKE '%田' 先頭の文字が決まらないと、木を降りる位置が決まらない 後方一致で探す設計を見直す
単一列の索引で IS NULL すべての列が NULL の項目は B-tree 索引に格納されない NOT NULL の列と組み合わせた複合索引にする
複合索引の先頭列に条件がない 2 列目以降は飛び飛びにしか並んでいない（5 節） よく使う条件の列を先頭にする

7. 索引の代償

索引は検索を速くするが、無料ではない。

  • 更新が遅くなる: 行を INSERT・DELETE するたびに、すべての索引の項目も追加・削除する。索引の列を UPDATE すると、項目を削除して正しい位置に入れ直す
  • 領域を使う: ORDERS の索引は 1 つあたり葉が 374〜531 ブロックあり、表（1000 ブロック）の半分前後の大きさがある
  • 重複した索引は無駄になる: (order_date) と (order_date, amount) があれば、前者でできることは後者でもほぼできる。先頭の列が同じ索引は統合を検討する

まとめ

  • 索引は「値 → ROWID」の組を値の順に並べた B-tree である。ルート・ブランチが目次、葉が本体で、葉どうしは隣とつながっている
  • 索引でたどり着けるのは ROWID（住所）までである。索引にない列が必要なら、表のブロックを読む
  • 検索の手間は、索引の段数（ほぼ一定）と、表を読むブロック数（ROWID の散らばり方しだい）の合計である
  • 複合索引は 1 列目の順に並び、2 列目は 1 列目が同じ範囲の中でしか並ばない
  • 複合索引に条件の列を含めると、表を読む前に索引の中で絞り込める。必要な列がすべて揃えば表を読まない
  • 複合索引の列は「等価条件の列を先、範囲条件の列を後」に並べる。先頭列の条件がなければ RANGE SCAN できない
  • 列に関数をかけたり、型変換を起こしたりすると、索引の順番が使えなくなる
